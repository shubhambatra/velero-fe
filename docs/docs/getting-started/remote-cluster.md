## 🚀 **Connecting to a Remote Cluster**

Velero UI does not have a separate "remote cluster" mode. It connects to Kubernetes the same way in every case — by loading a
[**kubeconfig**](https://kubernetes.io/docs/concepts/configuration/organize-cluster-access-kubeconfig/) file and, optionally,
selecting one of its contexts. A kubeconfig context simply points at an API server URL plus credentials — it doesn't matter whether
that server is on your laptop, in the same cluster Velero UI runs in, or on a completely different network. As long as the container
running Velero UI can reach the remote API server over the network, it works out of the box, with **no code changes and no special
configuration**.

This page shows how to point Velero UI at a remote cluster in each deployment method.

### ⚙️ How cluster selection works

Two environment variables control this, already documented on the [Environment Variables](/getting-started/environment-variables) page:

- **`KUBE_CONFIG_PATH`** — path to a kubeconfig file. If unset, Velero UI assumes it's running inside the cluster it manages and uses
  the pod's ServiceAccount instead (in-cluster mode).
- **`KUBE_CONTEXT`** — name of the context to use from that kubeconfig file. If unset, the kubeconfig's own `current-context` is used.

To connect to a remote cluster, mount a kubeconfig file that contains a context for that cluster, and set `KUBE_CONTEXT` to its name.
That's the entire mechanism — everything below is just this pattern applied to Docker, Docker Compose, Helm, and raw manifests.

:::tip Verifying which cluster you're connected to
Once running, open **Settings → Cluster** in Velero UI. It shows the API server address and the active kubeconfig context, so you can
confirm at a glance which cluster you're managing — especially useful when your kubeconfig has several contexts.
:::

### 🔑 Recommended authentication: static credentials, not exec-plugins

Kubeconfigs generated by cloud CLIs — `aws eks update-kubeconfig`, `gcloud container clusters get-credentials`,
`az aks get-credentials` — typically use an `exec:`-based credential plugin (`aws`, `aws-iam-authenticator`, `gke-gcloud-auth-plugin`,
`kubelogin`, etc.). These binaries are **not installed** in the official `otwld/velero-ui` Docker image, so a kubeconfig copied
straight from your machine will fail to authenticate inside the container, even though it works fine locally with `kubectl`.

For a long-running server like Velero UI, the simplest and most portable option is a **static credential**: a dedicated
ServiceAccount on the remote cluster, scoped to only what Velero UI needs, with a long-lived bearer token or client certificate
embedded directly in the kubeconfig. No CLI binaries, cloud credentials, or network calls to an identity provider are required at
runtime.

1. On the **remote cluster**, create a scoped ServiceAccount and bind it to the same permissions Velero UI's own in-cluster deployment
   uses (see [`kubernetes/manifests`](https://github.com/otwld/velero-ui/tree/main/kubernetes/manifests) for the reference
   `ClusterRole`/`Role` definitions — read/list namespaces, full access to `velero.io` resources, and log/pod access in the
   `velero` and `velero-ui` namespaces). Avoid granting `cluster-admin`.

    ```yaml
    apiVersion: v1
    kind: ServiceAccount
    metadata:
      name: velero-ui-remote
      namespace: velero-ui
    ---
    apiVersion: v1
    kind: Secret
    metadata:
      name: velero-ui-remote-token
      namespace: velero-ui
      annotations:
        kubernetes.io/service-account.name: velero-ui-remote
    type: kubernetes.io/service-account-token
    ```

   Apply the `ClusterRole`/`Role`/`RoleBinding`/`ClusterRoleBinding` manifests from `kubernetes/manifests`, updating their
   `subjects` to reference the `velero-ui-remote` ServiceAccount.

2. Read back the token and the cluster's CA certificate:

    ```bash
    TOKEN=$(kubectl get secret velero-ui-remote-token -n velero-ui -o jsonpath='{.data.token}' | base64 -d)
    CA=$(kubectl get secret velero-ui-remote-token -n velero-ui -o jsonpath='{.data.ca\.crt}')
    SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')
    ```

3. Assemble a static kubeconfig — no `exec:` block, no dependency on any CLI tool being present at runtime:

    ```yaml title="remote-kubeconfig.yaml"
    apiVersion: v1
    kind: Config
    clusters:
      - name: remote-cluster
        cluster:
          server: ${SERVER}
          certificate-authority-data: ${CA}
    users:
      - name: velero-ui-remote
        user:
          token: ${TOKEN}
    contexts:
      - name: remote-cluster
        context:
          cluster: remote-cluster
          user: velero-ui-remote
    current-context: remote-cluster
    ```

   Treat this file like any other credential — store it in a Kubernetes `Secret` or Docker secret, never commit it to source
   control or bake it into an image.

If your Docker image already includes the required cloud CLI (for example, a custom image built on top of `otwld/velero-ui` that
installs `aws-iam-authenticator`), an `exec:`-based kubeconfig will also work — the static-credential approach above is simply the
path that requires no image customization.

### 🐳 Docker

Mount the remote kubeconfig and point `KUBE_CONFIG_PATH`/`KUBE_CONTEXT` at it, exactly as you would for a local cluster:

```bash
docker run --name velero-ui \
  -v /path/to/remote-kubeconfig.yaml:/app/.kube/config \
  -e KUBE_CONFIG_PATH=/app/.kube/config \
  -e KUBE_CONTEXT=remote-cluster \
  -d -p 3333:3000 otwld/velero-ui:latest
```

If your kubeconfig has several contexts (for example a local one merged with a remote one), `KUBE_CONTEXT` is how you tell Velero UI
which one to use — see the [Docker guide](/getting-started/docker) and the [`docker-compose.yml`](/getting-started/docker#-installation-with-docker-compose)
example for the local-cluster equivalent of this same pattern.

### ☸️ Helm

The chart already exposes generic `volumes`, `volumeMounts`, and `env` values — no chart changes are needed to mount a remote
kubeconfig.

1. Store the kubeconfig as a Secret in the cluster where Velero UI itself runs:

    ```bash
    kubectl create secret generic velero-ui-remote-kubeconfig \
      --from-file=config=./remote-kubeconfig.yaml \
      --namespace velero-ui
    ```

2. Reference it from `values.yaml`:

    ```yaml
    env:
      - name: KUBE_CONFIG_PATH
        value: /kube/remote/config
      - name: KUBE_CONTEXT
        value: remote-cluster

    volumes:
      - name: remote-kubeconfig
        secret:
          secretName: velero-ui-remote-kubeconfig

    volumeMounts:
      - name: remote-kubeconfig
        mountPath: /kube/remote
        readOnly: true
    ```

3. Install or upgrade as usual — see the [Helm guide](/getting-started/helm):

    ```bash
    helm upgrade --install velero-ui otwld/velero-ui --namespace velero-ui --values values.yaml
    ```

:::info
Because Velero UI is only reading Velero/Kubernetes resources on the **remote** cluster, the ClusterRole/ClusterRoleBinding that the
chart creates in **its own** cluster (`rbac.clusterAdministrator`) is unrelated to remote-cluster permissions — those live entirely
in the ServiceAccount you created on the remote cluster in the authentication section above. You can leave the chart's own RBAC
settings as-is.
:::

### ⚙️ Raw Kubernetes Manifests

The manifests in [`kubernetes/manifests`](https://github.com/otwld/velero-ui/tree/main/kubernetes/manifests) default to in-cluster
ServiceAccount authentication (no kubeconfig at all) and have no built-in override hook, so add the Secret, volume, volumeMount, and
env vars to `deployment.yml` directly:

```yaml title="kubernetes/manifests/deployment.yml"
spec:
  template:
    spec:
      containers:
        - name: velero-ui
          env:
            # ...existing env vars
            - name: KUBE_CONFIG_PATH
              value: /kube/remote/config
            - name: KUBE_CONTEXT
              value: remote-cluster
          volumeMounts:
            # ...existing volumeMounts
            - name: remote-kubeconfig
              mountPath: /kube/remote
              readOnly: true
      volumes:
        # ...existing volumes
        - name: remote-kubeconfig
          secret:
            secretName: velero-ui-remote-kubeconfig
```

Create the `velero-ui-remote-kubeconfig` Secret the same way as in the Helm example above, then `kubectl apply -f .` as described in
the [Kubernetes guide](/getting-started/kubernetes).

## 🔒 Security Notes

- Grant the remote ServiceAccount only what Velero UI needs (see the reference `ClusterRole`/`Role` in
  [`kubernetes/manifests`](https://github.com/otwld/velero-ui/tree/main/kubernetes/manifests)) rather than `cluster-admin`.
- Store kubeconfigs and tokens as Kubernetes `Secret`s or Docker secrets — never in a ConfigMap, image layer, or source control.
- Rotate the remote ServiceAccount's token periodically; since it's a static credential, treat it with the same care as a database
  password.
- Network access matters too: the remote API server must be reachable from wherever Velero UI runs (VPN, private link, public
  endpoint with IP allow-listing, etc.) — this is unrelated to Velero UI itself and follows your existing network/cluster
  connectivity setup.

## 🧭 Multiple Clusters

A single running instance of Velero UI manages exactly one cluster at a time — the one selected via `KUBE_CONFIG_PATH`/`KUBE_CONTEXT`
(or in-cluster mode). To manage several clusters today, run one Velero UI instance per cluster, each with its own configuration.
Switching which context an instance uses requires updating its configuration and restarting it; there is currently no in-app cluster
switcher. If you need to manage many clusters from a single UI session, please open a discussion on
[GitHub](https://github.com/otwld/velero-ui/issues) — this is tracked as a possible future enhancement.
