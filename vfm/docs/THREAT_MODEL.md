# Threat model

Velero Fleet Manager (VFM), PLAN.md §12.3. Written on M7 day 36 from a read of the code and its tests, not from the design
documents: every row says where the mitigation is and what proves it. Each mitigation is verified by an **automated test**
(`T:` file and test) or a **documented manual check** (`M-n`, section 7). A row with neither is listed as a gap in section 8.

Status of the milestone this belongs to: M7 day 36. Fixes made while writing it are in section 9.

## 1. What is being protected

| Asset                                                                                                                       | Why it matters                                                                                      |
| --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Customer clusters (the agent can create, restore and delete Velero objects)                                                 | A restore writes into production; a delete removes recovery points.                                 |
| Backup data in the customer's object storage                                                                                | VFM never proxies it (PLAN P2); it only holds the _credentials_ it was told to write into a Secret. |
| Cloud credentials in Velero's namespace                                                                                     | Reachable by the agent's Secret rule (accepted risk A-2).                                           |
| Platform secrets: `VFM_MASTER_KEY`, the internal CA key, OIDC client secrets, channel URLs and signing secrets, MFA secrets | Whoever holds them can impersonate agents, read stored secrets or forge sessions.                   |
| Identity: sessions, API tokens, MFA                                                                                         | The way into everything above.                                                                      |
| Org isolation                                                                                                               | One tenant must never read or change another's data.                                                |
| The audit log                                                                                                               | The record of who did what; it has to be believable.                                                |

## 2. Components and trust boundaries

```
 Browser ──HTTPS──▶ [ingress / TLS] ──▶ Control plane API (NestJS, N replicas) ──▶ Postgres
                                           │        │                              Redis (sessions, pub/sub, throttles)
                                           │        └─ outbound: alert webhooks, OIDC IdP, SMTP
                                           └─ gRPC gateway (mTLS) ◀──── Agent (in each customer cluster) ──▶ kube-apiserver / Velero
```

Trust boundaries, in the order an attacker meets them:

1. **Internet → ingress/API.** Anyone. Authenticated by session cookie or API token.
2. **Browser content.** Agent-supplied and log-derived text is _data_, never markup.
3. **API → Postgres / Redis.** One trust domain; reachable only from the control plane's network (M-1).
4. **Agent → gateway.** The agent is **semi-trusted** (PLAN §12.1): a compromised cluster must not corrupt another cluster's
   data or inject script into the UI. Identity is the client certificate, nothing the agent says.
5. **Gateway → agent.** The control plane is **not trusted by the agent** for the cluster owner's policy: the owner's
   ConfigMap decides what the agent will do, whatever the control plane asks.
6. **Control plane → outbound destinations.** An org Admin names the URL; the control plane connects from inside the
   operator's network (SSRF).

Actors: anonymous internet user; authenticated member (any role); org Admin (can name destinations, create providers and
channels); person with a stolen session cookie or phished password; compromised agent / cluster; hostile object-store or
BackupStorageLocation; operator (trusted); a control plane that has been compromised (the agent's defence).

## 3. Assumptions

- TLS terminates in front of the control plane in production, and the API is not reachable over plain http (M-3).
- Postgres and Redis are not reachable from outside the control plane's network, and Redis requires a password (M-1).
- The operator keeps `VFM_MASTER_KEY` secret and backs it up; losing it loses the stored secrets.
- Container hardening of the control plane is the operator's until the chart exists (day 41, M-2).

## 4. Method

STRIDE per component. A threat is **mitigated** when the cell names a mechanism and a verification, **accepted** (section 8,
A-n) when the risk is understood and left, and a **gap** (section 8, G-n) when it is neither, with the day that will close it.

Verification references use `T:` for tests. Server tests are Vitest (`server/src/**.test.ts` unit, `server/test/*.e2e.test.ts`
against real Postgres and Redis), agent tests are Go (`agent/internal/**`). A test name is given where it makes the claim
unambiguous.

## 6. Authentication and authorization route inventory

The global guards apply to every route. The `@Public()` routes, each with its reason:

| Route                                                 | Why it is public                                                  | Limits                                                                  |
| ----------------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `GET/POST /auth/setup`                                | First-run bootstrap, gated by a one-time token printed to the log | token hash in Redis, single use; **G-3** no rate limit                  |
| `POST /auth/login`                                    | It is the login                                                   | per-account and per-IP throttles                                        |
| `GET /healthz`, `GET /readyz`                         | Orchestrator probes                                               | return no data                                                          |
| `GET /auth/oidc/providers`, `/:id/start`, `/callback` | Starting and finishing a login                                    | state and nonce, PKCE; issuer is guarded (C11); 60 a minute per address |
| `POST /invites/register`                              | Accepting an emailed invitation                                   | the invitation token is the credential                                  |

`@AllowsMfaPending` is limited to the MFA routes, sudo and logout. Routes using `checkInHandler` defer the permission check to
the service; each is covered by its feature's e2e, and `security-matrix.e2e` now covers every operation of the contract at once.

## 8. Accepted risks and open gaps

**Accepted** (understood, left, with the compensating control):

| #   | Risk                                                                                                                                                                             | Why accepted, and what limits it                                                                                                                                                                                |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A-1 | A compromised agent can lie about its own inventory and policy to the UI                                                                                                         | It cannot reach another cluster (C7-T) or change what other users may do; the agent enforces its own policy whatever the UI shows.                                                                              |
| A-2 | The agent can read and update every Secret in Velero's namespace, including Velero's cloud credentials                                                                           | PLAN §12.2 requires Secret create/update/get there (Kubernetes cannot scope `create` by name). | A-4 | The audit write is best-effort after the response                                                                                                                                | A crash between response and insert loses one event; the request log (with request id) still has the call. | A-6 | Org Admins can register an IdP and JIT-create accounts for addresses they assert                                                                                                 | Linking into existing accounts needs an existing membership (C2-S), and an invitation is accepted only with its emailed token, so an asserted address does not give access to another org.                      |
